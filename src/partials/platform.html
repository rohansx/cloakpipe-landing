Platform · The open core, deconstructed

Four surfaces.
One open core.

CloakPipe is built as four distinct product surfaces — the Rust proxy, the encrypted vault, the agent-hop policy engine, and the verifiable evidence ledger. The proxy is currently MIT licensed. The vault, signed evidence path, release certification, and release-aware runtime enforcement are implemented, as are external anchoring and the per-release audit pack. KMS, SSO, and enterprise deployment packaging are roadmap work.

Surface 01 · Proxy

The Rust proxy.
Open source core.

Browse the repo →

A Rust-native reverse proxy that intercepts AI API calls, pseudonymizes outbound data, and rehydrates inbound responses in real-time. Sub-50 ms p95 is a design target, not a universal guarantee; Eight Rust crates compiled to a single native binary. Your application changes exactly one line: the base URL.

OpenAI-compatible API

Change your base URL from api.openai.com to your CloakPipe endpoint. No other code changes. Works with LangChain, LlamaIndex, CrewAI, curl, and any OpenAI-compatible client.

Streaming SSE rehydration

LLMs stream token-by-token. CloakPipe maintains a sliding window, detects pseudonymized tokens mid-stream, looks up real values from the vault, and splices them in — without buffering or breaking the SSE contract.

Multi-provider routing

Route to OpenAI, Anthropic, Google, AWS Bedrock, Azure OpenAI, or any self-hosted model via vLLM or Ollama. Apply different masking policies per provider — strict for closed models, lighter or bypassed for self-hosted.

Native MCP server

A Model Context Protocol server exposing mask_text, mask_file, unmask_in_context, and scan_directory tools. AI agents can call CloakPipe directly as a tool from Claude Desktop, Cursor, or any MCP client.

Pluggable, tiered detection pipeline

Detection is deliberately commoditized — CloakPipe does not lock you into a single model. The proxy runs a tiered pipeline where each tier escalates only as needed: what regex catches deterministically, the neural models never see; what one model misses, the ensemble catches. OpenAI Privacy Filter scores 96% on synthetic benchmarks but Tonic.ai measured 18–65% on real-world EHR notes, call transcripts, and loan contracts. No single model catches everything — which is why the pipeline tiers.

Surface 02 · Vault

Reversible by design.
You hold the keys.

Why reversibility matters →

An encrypted tokenization vault that stores the mapping between real sensitive data and pseudonymized tokens. The vault is the source of truth — and the reason pseudonymization is reversible under policy, not a one-way redaction. Without a vault, data goes in and nothing useful comes out.

AES-256-GCM at rest

Every real value stored in the vault is encrypted with AES-256-GCM. Nothing real exists outside the vault — the clean prompt that reaches the provider contains zero original sensitive data.

Customer-managed keys · roadmap

The current vault supports local encryption keys. AWS KMS, GCP Cloud KMS, Azure Key Vault, and Vault Transit adapters are planned.

Deterministic + format-preserving

The same input always produces the same token within a tenant's scope, preserving entity consistency across conversations and batches. Format-preserving FF1 (NIST SP 800-38G) keeps cards Luhn-valid and emails email-shaped.

Per-tenant isolation

Each customer gets their own vault namespace with their own encryption keys. No cross-tenant data access is possible at the cryptographic level.

TTL & session scoping

Tokens can expire after a single conversation, after a configurable TTL, or persist indefinitely for ongoing workflows. Scope the lifetime to the sensitivity of the workload.

Automatic key rotation · roadmap

Rotation policy and managed key-version migration are planned and are not yet production capabilities.

Release control · Across every surface

Only certified releases
reach production.

How the evidence verifies →

An Agent Release pins code, prompt, model, tools, retrieval, and policy to one canonical sha256 manifest hash. Evaluation results, the certification, runtime decisions, and ledger records all refer to that hash, so the release that passed is the release that runs.

Agent Release manifests

cloakpipe release validate, hash, diff, inspect, and register. A diff maps each changed component to the assurance suites it requires. The cloud registry keeps releases and baselines.

Imported evaluation evidence

cloakpipe eval import converts JUnit XML, Braintrust experiments, and Langfuse dataset runs into a native EvaluationRun. Scoring fails closed: an unscored case is an error, and a pass needs every score above the threshold.

Signed certification

A deterministic decision over critical failures, pass-rate regression against the baseline, suite coverage, and metric rules. Signed as an Ed25519 DSSE envelope bound to the manifest hash, verified offline, revocable, and runnable as a GitHub Action.

Production promotion gate

Promoting a release to production requires a valid certification. A break-glass override is possible, but it is recorded with its reason.

Scoped API keys

Keys are scoped to an agent and an environment. The server picks the release from that environment's pointer, not from the caller, and runtime keys cannot write to the registry.

Production sentinels

SLO rules over live calls: error, guardrail-block, and policy-deny rates, with a minimum call count and a time window. A breach raises an alert or revokes the release automatically.

Surface 03 · Agent-Hop Policy

Every hop,
decided outside the model.

Every decision is sealed as evidence →

LLM provider hops and MCP tool calls receive a deterministic decision outside the model. Cedar policies see the release context: whether a release is bound, what it declares, its certification status, and its environment. Sub-agent messages, conduct rules, and regulatory policy packs are still roadmap work.

Release-aware decisions

Requests from a revoked release are blocked. Unmasking requires a certified release; otherwise the response stays pseudonymized. Provider masking rules still apply per hop: "mask all patient names when routing to external models."

MCP tool gate

cloakpipe mcp-proxy --manifest --certification allows only the tools a certified release declares and refuses anything it cannot parse (JSON-RPC -32001). Every hop is recorded in the signed ledger, bound to the release hash.

Conduct policy · roadmap

Planned: calling-hour windows, mandatory-disclosure verification, session sequencing — behavioral rules no redactor touches. A 7:05pm call is recorded as a reportable event, deterministically, every time.

Context-based access (CBAC)

Unmasking decided at runtime from who is asking, their role, the data's sensitivity, and the workflow context. A sales agent cannot unmask medical records; a supervising physician can — but only during an active case review, and only from a certified release.

Custom entity definitions

Define domain-specific entity types via regex, keyword lists, or NER labels: medical record numbers, case docket IDs, insurance policy numbers, internal employee IDs — whatever your domain requires.

Policy packs

The India DPDP pack in CloakPipe Cloud enforces purpose, consent, children's data, and cross-border rules in Cedar at the proxy, and records every decision in the ledger. It is a technical control, not legal advice. An RBI conduct pack is planned.

Example policy — patient data for external models

# rules — evaluated top to bottom on every request - name: mask_patient_data_for_external_models when: provider: [openai, anthropic, google] entity_type: [PERSON, DIAGNOSIS, MEDICATION, MRN] action: pseudonymize # self-hosted models stay inside the perimeter — pass through - name: allow_internal_models_unmasked when: provider: [internal-vllm, self-hosted] action: passthrough # only clinicians may reverse clinical entities — CBAC enforced - name: restrict_unmask_to_physicians when: action: unmask entity_type: [DIAGNOSIS, MEDICATION] require_role: [physician, clinical_admin]
Surface 04 · Evidence Ledger

Every decision
sealed. Verify it yourself.

See the compliance posture →

A hash-chained, signed ledger records privacy-relevant proxy decisions and supports offline bundle verification. It records what types of data were processed, never the values. Exported bundles are anchored to a public RFC 3161 timestamp authority and the Sigstore Rekor transparency log, and both receipts verify offline.

What gets sealed

Every request (timestamp, caller, source IP, destination provider), every detection event, every masking action, every unmask request, every policy evaluation, and every MCP tool hop — hash-chained, Ed25519-signed, and bound to the release hash.

External anchoring

cloakpipe anchor timestamps a signed batch head at an RFC 3161 authority and in Sigstore Rekor. The verifier checks both receipts offline against a TSA root and Rekor key you pin; revocation (CRL/OCSP) is not checked. CloakPipe Cloud does not anchor its ledger automatically yet.

Open verifiers · audit pack

Auditors check chain integrity, signatures, anchors, and certifications offline with the open CLI. A signed per-release audit pack bundles the manifest, evaluations, certifications, governance history, and ledger, and verifies offline too.

Compliance workflows · roadmap

The ledger can support audit workflows, but CloakPipe is not certified for HIPAA, SOC 2, PCI-DSS, GDPR/DPDP, or the EU AI Act.

Architecture · The hot path

One request.
One hot path.

Read the architecture docs →

Every prompt, response, and tool call passes the same per-request hot path: authenticate, evaluate policy, detect, pseudonymize and write to the vault, forward a clean prompt, stream back, rehydrate, and seal an evidence record. All of it in Rust, transparently, with a sub-50 ms p95 target.

REQUEST FLOW · PER-REQUEST · < 50 MS TARGET
Auth → Policy → Detect → Vault → Forward → Rehydrate → Ledger
Built on Rust / Axum / Tower with Tokio streams. Detection escalates through tiers; the vault makes the round-trip reversible; the evidence ledger closes every request.
  • 1 · Auth — a scoped API key resolves the agent, the environment, and its current release
  • 2 · Policy — Cedar evaluation with release context: allow / deny plus per-entity and per-hop rules
  • 3 · Detection — T1 regex + checksum (<1ms) → T2 Privacy Filter (ONNX, 30–50ms) → T3 GLiNER2 for custom entities (optional)
  • 4 · Pseudonymize + vault write — deterministic tokens encrypted at rest
  • 5 · Forward — clean prompt to the LLM provider; zero real data leaves
  • 6 · Stream + rehydrate — detect tokens in the SSE stream, vault lookup, authorize, splice real values back
  • 7 · Ledger — hash-chain and sign a privacy-safe evidence record, then return the response with real values restored

Core technology choices

Component Technology Why
Proxy runtime Rust / Axum / Tower Sub-millisecond overhead per request. Zero-cost abstractions. Memory safety without GC pauses.
ML inference ONNX Runtime (ort) Run Privacy Filter and GLiNER2 locally on CPU or GPU. No Python dependency in the hot path.
Tokenization HF tokenizers (Rust) Fast model-input preparation, shared across the detection pipeline.
Vault encryption AES-256-GCM · AES-SIV · FF1 GCM for general encryption, SIV for deterministic tokens, FF1 (NIST SP 800-38G) for format-preserving values.
Key management Local keys · KMS planned Local encryption keys today. Customer-managed KMS and automatic rotation are roadmap, not shipped.
Token registry PostgreSQL (sqlx) Deterministic token lookup with per-tenant isolation. Proven at scale.
Policy engine Cedar Formally-verified Rust crate, not a homegrown DSL. Policies see the release context; git-versioned and diffable.
Certification Ed25519 · DSSE · in-toto Standard signed envelopes bound to the manifest hash, verifiable offline without CloakPipe.
Observability OpenTelemetry-rust Traces, metrics, and logs over Tokio streams, exportable to any OTEL collector.
