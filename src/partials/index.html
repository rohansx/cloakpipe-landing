Agents take actions.
Three things go wrong.

Agents in production send email, write to databases, issue refunds and call internal APIs. Observability tools show you what happened afterwards; they stop nothing. Identity tools name the agent; they do not limit what it does. The missing piece is an enforcement point on the action itself.

FIG 0.1

The agent is tricked

Prompt injection arrives through tickets, web pages and documents. A filter in front of the model will never catch all of it. A check on the resulting tool call does not need to.

FIG 0.2

The agent is over-permissioned

It holds a long-lived credential, so one bad call can reach anything the token can. A contract limits which tools and which argument values get through the gate.

FIG 0.3

The agent repeats itself

A call times out, the agent retries, and the customer gets two refunds or two invoices. Side effects need a state, not a blind retry.

01

Declare

A tool contract lists the tools the agent may call and the shape of every argument: types, lengths, ranges, patterns, and values that must match the current task. It is closed by default: an undeclared tool or argument is refused. An optional Cedar policy adds what one call cannot show: rate limits over persistent counters, tiers and time windows.

02

Enforce

Every tools/call is checked before it is forwarded. Refused calls get a structured JSON-RPC error the agent can read, and the tool never sees them. Risky calls, such as a refund over $100, wait for an approval bound to the exact arguments. Errors fail closed. --mode shadow lets you watch before you enforce.

03

Prove

Every decision, allowed or refused, is an entry in a hash-chained ledger that never stores raw argument values, and each entry is signed with the gate's Ed25519 key. The gate seals entries into epochs and timestamps each one with an RFC 3161 authority and Sigstore Rekor. cloakpipe verify checks an exported audit pack offline.

02 · Agent trickedShipping

Wrong recipient, refused

Hidden text in a ticket makes the agent call send_email to attacker@evil.com. The recipient is not the ticket's customer, so the gate refuses with scope_mismatch (JSON-RPC -32001). The email server never sees it. A call to an undeclared export_customers is refused as undeclared_tool.

Slack and PagerDuty alerts on denials are on the roadmap.

03 · Risky but legitimateCLI approval today; Slack approvals on roadmap

A refund needs a human

The contract says a refund over $100 needs approval. A $350 refund is refused with approval_required until someone signs an approval for that exact call with cloakpipe approve. The agent retries and the gate forwards it. Reusing that approval for a different amount fails with approval_invalid.

The refusal names the approvers and the call's fingerprint, but nothing delivers the request yet: an approval broker and Slack approvals are on the roadmap.

04 · Did it happen?Shipping · manual reconcile

Reconcile before retry

A create_invoice call is sent but the answer never comes back. The gate marks the operation unknown and refuses every retry with reconcile_before_retry until an operator records what happened with cloakpipe operations reconcile. A retry of a call that already succeeded gets the stored result instead of a second invoice.

Today the outcome turns unknown when the gate or the tool server stops mid-call. Per-call timeouts and reconciliation hooks are on the roadmap.

What it is not

A gate is useful because it is small and predictable. These are the things it deliberately does not try to be.

Not a prompt filter

It does not read prompts or classify content. There is no model and no classifier in the decision, only the contract and the call.

Not a governance platform

It does not inventory your agents, issue identities or draw compliance charts. It produces the evidence those systems can use.

Not a sandbox

It cannot stop an action that never becomes a tool call through the gate, or a compromise of the host below it.
